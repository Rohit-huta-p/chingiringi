## ⚠️ Branch Rules — READ FIRST


## How Parallel Agents Work

You run multiple `claude` sessions simultaneously — each in its own terminal tab or IDE window — all pointing at the same repo. They work on different files so there are no merge conflicts. When one finishes, you commit, and the next agent reads this file to know what's done.

**Daily workflow:**
```
Terminal 1: claude   ← Agent A (e.g. Buyer track)
Terminal 2: claude   ← Agent B (e.g. Backend track)
```
Both read the same codebase. Each writes to its own assigned files. You commit Agent A's work, then Agent B's, no conflicts.

## Key Architecture Decisions

1. **BuyerTabNavigator** is an adaptation of the existing `DrawerNavigator.tsx` MobileNavigator. Copy the MobileTabBar component and 5-tab structure. Swap the "Home" tab target to `LiveDiscoveryScreen`. Rename "Videos" to "Cashback" and point it at `MobileHomeScreen` (the existing deals/cashback feed). Everything else is identical.

2. **SellerTabNavigator** is a fresh 4-tab navigator using the same MobileTabBar design but with `Colors.orange` (`#F97316`) for active state instead of `Colors.primary` (`#4784E2`).

3. **`user.role`** in the Zustand store is already typed as `role?: string`. Update `UserType` to `role?: 'buyer' | 'seller' | 'admin' | null`. The RootNavigator reads this and branches.

4. **LiveDiscoveryScreen** has two toggle pills: "Live" and "Stores". Live tab shows stream cards from `GET /streams/active` + real-time updates via Socket.io. Stores tab renders the existing `OfflineStoresScreen` inline. Followed stores appear first when live.

5. **StoreDetailScreen** gets an `isOwner` prop. When true (seller viewing their own store), it shows Edit controls and links to `MyStoreScreen`. When false (buyer), it shows the Follow button.

6. **Daily.co**: broadcaster calls `POST /streams/token`, gets a Daily.co room URL + token, initialises `DailyMediaView` and `DailyCall`. Viewer calls `POST /streams/:id/viewer-token`, joins as viewer. Both use `@daily-co/react-native-daily-js`.

- `getStoreStats` dynamically imports `mongoose.model('Product')` to avoid a circular dependency with the products module — it will return `totalProducts: 0` until Product documents reference `storeId`.

- `unfollowStore` uses a MongoDB pipeline update to floor `followerCount` at 0: `$max: [0, $subtract: [$followerCount, 1]]`.
- Stream model is scaffolded only; Daily.co room creation (`dailyRoomName`, `dailyRoomUrl`) and the broadcaster/viewer token endpoints are E2's job in Sprint 3.

#### Socket.io pattern for D1 / D2
```
// Connect (frontend)
const socket = io('wss://your-api.com/stream', {
  auth: { token: accessToken },   // optional — guests connect without token
});

// Broadcaster / Viewer join
socket.emit('join_stream', { streamId: '...' });

// Viewer receives
socket.on('viewer_count_update', ({ streamId, count }) => { ... });
socket.on('heart_burst',         ({ streamId, count }) => { ... });
socket.on('new_chat',            ({ streamId, user, text, timestamp }) => { ... });
socket.on('stream_ended',        ({ streamId, storeId }) => { ... });

// Viewer sends
socket.emit('heart_reaction', { streamId });
socket.emit('chat_message',   { streamId, text: 'Love this!' });
socket.emit('leave_stream',   { streamId });
```

#### Gotchas
- `endStream` does a **dynamic import** of `server.js` to get the `io` instance and avoid a circular dependency at module-load time. The import is wrapped in try/catch so tests that don't boot the HTTP server still work.
- Heart reactions use a **500 ms accumulation window** before broadcasting `heart_burst`. This batches rapid taps into a single event to avoid flooding clients. The counter map is keyed by room string (`stream:<id>`).
- Socket auth is **optional** — `socket.data.user` may be `null` for unauthenticated viewers. `chat_message` falls back to `'Guest'` as the display name.
- Daily.co REST calls use Node's built-in `fetch` (Node 18+). If your Node version is older, add `node-fetch`.
- Set `DAILY_API_KEY` in your real `.env` before testing `POST /api/streams`.

#### useSocket gotchas
- Connects to `${baseURL}/stream` (the `/stream` Socket.io namespace, not the root namespace). LiveDiscoveryScreen currently connects to the root namespace — it won't receive events from `/stream`. If viewer-count updates need to reach the discovery screen, the backend should emit them on both namespaces, or LiveDiscovery should be updated to join `/stream` too.
- Token is read async before the socket connects so the initial handshake carries Bearer auth. If `SecureStore.getItemAsync` throws (e.g. first boot), the socket still connects as an unauthenticated guest — chat falls back to `'Guest'` display name.
- `cbRef` pattern: callback changes never reconnect the socket. If `streamId` changes (e.g. the user watches two streams back-to-back in the same component mount), the old socket is disconnected and a fresh one is created.
- `leave_stream` is emitted before `disconnect()` so the backend can atomically decrement viewer count before the connection closes (avoids the `$max:[0,...]` floor kicking in too early on rapid reconnects).

#### LiveChatSheet gotchas
- NOT the existing `CommentsSheet` (which is REST API-backed for pre-recorded video comments). LiveChatSheet is a self-contained socket-driven component defined inside ViewerScreen.
- Messages are capped at 100 (`prev.slice(-99)`) to avoid unbounded memory growth on long-running streams. A future improvement: virtualised / windowed list.
- `isMe` check uses `me?.name === msg.user.name` (display-name string comparison). This is imprecise if two users share a name. Replace with `me?.id === msg.user._id` once the backend includes `_id` in `new_chat` events.

#### FloatingHeart gotchas
- Hearts are capped at `MAX_HEARTS = 20` in-flight at once; a server burst (`heart_burst { count: 500 }`) is clamped to 5 new hearts per event.
- Each heart cleans up its own `setTimeout` callbacks on unmount (component removed from the `hearts` array before timers fire is safe — `clearTimeout` is a no-op on an already-fired timer).
- `xOffset` scatters hearts from −10 px to +50 px right of the heart button origin. Adjust `right: 24 + item.xOffset` in `floatingHeart` style if the heart button is repositioned.
